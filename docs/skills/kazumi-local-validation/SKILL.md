# Kazumi 仓库开发与验证

## 接手与范围

- 先读取当前任务及必要的历史结论，检查实际 Git 根目录、分支和未提交改动；保留已有工作，接着已确认的根因和未完成项推进。
- 当前工作区外层包含 `outputs/Kazumi-s-book`（实际仓库）和 `work`（工具及临时证据）；先确认目录，不在外层递归扫描 Flutter SDK、构建产物或历史日志。
- 按需查阅 `docs/novel/` 中与当前任务有关的方案和最新验收记录。历史测试通过不能替代当前代码的验证，未读到的历史不得声称已完整掌握。

## 模块隔离与简单实现

- 定制需求按附加功能实现，优先使用独立模块和清晰接口；只保留必要的入口接入，避免让官方功能依赖新增业务状态。
- 不改变官方原有分支及既有功能行为。定制工作留在当前授权的定制分支，不向 `upstream` 推送，也不擅自修改 `main`。
- 小说规则、阅读器、书架、阅读进度及同步逻辑保持在小说模块内；接入搜索、详情、追番和设置时采用最小改动，检查未启用或未使用小说功能时原流程仍正常。
- 追番快速播放复用详情页已有的 `WatchEntry.open` 选源和播放入口。播放器、解码、渲染及播放控制保持官方逻辑，不因测试故障修改它们。
- 不引入兜底路径或防御性编程；不吞异常、静默切换实现、重复盲点或放宽断言来掩盖失败。效果未达成时查明并修复具体原因。
- 避免为简单需求引入额外框架、重复流程或不必要的抽象。

## 局部编辑与低噪声操作

- 禁止删除整个文件后重新生成，只用局部补丁；保留原编码、换行和已有修改。
- 读取文件按调用链、符号和相关行段展开，不全量读取大文件。
- 使用限定目录的 `rg` 搜索；目录列表、复制、构建和测试等可能产生大量输出的命令，提前限制输出或重定向到临时日志，只回传结论及必要错误片段。
- 临时实验、下载、日志及截图放在明确的工作目录，不混入生产模块；清理前核对具体路径和用途，保留正式回归测试及必要证据。

## 根因与回归验证

- 已正常工作的流程在修改后出错，首先检查上一步改动是否造成回归。
- 修复方案必须建立在根因和复现实验上：保留修复前失败证据，再用相同有效断言确认修复后通过；不能用局部绕过覆盖根因。
- DNS、网络、工具链、模拟器和脚本问题分别定位，不通过改生产域名、添加 DNS 规则、扩大超时或更换业务路径掩盖环境问题。
- 测试使用真实生产入口和依赖注册，外部网络或系统边界需要替身时明确证据范围；拆除原生依赖的独立探针不能算完整项目测试通过。

## 本地先通过，再触发 GitHub

- 先在本地完成当前变更的静态分析、回归测试及能在本机执行的检查，再触发 GitHub Actions。用户已明确授权本机不能开启虚拟化且暂无真机期间，Android 原生验收继续使用 GitHub 模拟器；Windows 和通用测试继续本地执行，Android 例外不代表可跳过发布门槛。
- 本地失败就在本地定位、修复和回归，不把 GitHub 工作流当作反复调试脚本的环境，避免连续失败邮件。
- 安装工具前先核对安装注册信息、用户指定目录及必需组件，复用已有环境，只补缺失部分；不能仅检查默认路径就断言未安装。工具链版本与项目要求及已验证的 CI 环境核对。
- 当前机器暂不能开启虚拟化，保持 Hypervisor 启动项关闭。Android 使用获准的 GitHub 原生测试工作流，触发前先修复可本地复现的脚本问题，只运行必要任务；失败后检查证据再决定下一次运行，不盲目重跑，也不把编译成功算作原生操作通过。
- 缺少本地工具链时先核对并补齐所需组件；除上述已授权的 Android 云端验收外，不以云端运行或缩减测试代替。未完成的验证仍记为未完成。
- 本地结果必须对应准备推送的代码。验证后再修改受测代码或脚本，需要重新验证受影响部分，不能沿用旧结果。
- 不擅自关闭账号全部通知，也不靠关闭测试、忽略失败或移除发布门槛减少邮件。
- 全部发布门槛通过后，按已有授权清理临时测试文件并发布；正式回归测试要保留。构建成功、测试成功、原生操作成功及发布成功分别记录。

## 快速交互测试

- 点击、滑动等普通连续验证操作间隔不超过 2 秒；优先以可见状态或明确条件驱动下一步，不插入固定长时间等待。
- 播放验证通常观察 5–10 秒，核对走时及画面；暂停、恢复、切集分别验证，不无目的地长时间播放。
- 不给每一步套用 30–60 秒的通用等待。启动、下载或真实网络等无法按普通交互完成的步骤，按实际条件短间隔检查，明确必要超时及耗时原因。
- 超时后保存有限现场并定位原因，不盲目重跑整套。先复验失败步骤及其相关路径，最后执行必要的完整回归。
- Android 自动化需检查操作工具自身的稳定等待；控制栏自动隐藏等时序必须匹配真实应用，不为脚本方便修改产品行为。

## 覆盖率与交付证据

- 新增及修改代码的路径覆盖目标至少 90%；使用可测量的分支覆盖率，并以操作矩阵补充入口和跨模块路径。行覆盖率或测试数量不能代替路径覆盖结论。
- 使用完整项目的 `flutter test --branch-coverage` 收集数据，明确统计基准、纳入的新增/修改文件、已覆盖和未覆盖分支；不通过扩大无关分母或排除难测代码凑比例。
- 同时覆盖适用的正常、取消、失败、重试、返回、重复进入及异步时序分支；验证新增功能不会破坏原有入口、状态和数据。
- 既有定制功能接手时也要明确覆盖缺口。没有报告或报告不足 90% 时如实标记未达标，不凭历史测试通过数量宣称满足要求。
- 测试针对真实行为和可观察结果，避免只复述实现的无效用例。原生安装包、平台、版本和操作证据不可相互替代。
- 交付说明写清改了什么、为何修改、实际验证结果、未覆盖项及下一步；不能将待验证事项写成已完成。
