## 新增同步整改设计（用户已要求实施，产品代码尚未由本审查修改）

### 已核对根因与边界

实际模型文件是 `lib/novel/novel_sync_state.dart`，没有独立的 `novel_sync.dart`。`NovelWebDavExchange.run` 每次发布完整不可变快照，只增加不回收；`NovelService.sync` 将已见文件名无限累加。`webdav.dart:105` 与 `novel_service.dart:548` 都固定 `/kazumiSync/novels/v1`，后者还把路径加入本地 seen 的 scope。

`novel_entry.dart:18,88–89` 要求先解决全局全部冲突；`novel_library_page.dart` 以全局 `conflicts.isEmpty` 控制整个书架和进入阅读。不能仅删除这几条判断：`selectedBook`、`work`、`position`、`mappedChapter`、`boundEditions` 和 `editionForBook` 仍有会读取冲突记录的调用点，必须按操作真正依赖的 key 分类处理，否则会从“全局阻断”变成局部抛错。

### 1. 快照回收：压缩文件，保留完整因果状态

最小方案保留现有多值寄存器、JSON schema `version: 1`、不可变文件命名和 PUT→MOVE 发布方式；新增一个明确的整理阶段，不改变“进度不取最大”的语义。

1. 整理以一次目录枚举得到的固定候选集合 C 为边界。读取并验证参与删除证明的每个快照（文件名哈希、schema、相同时钟对应内容一致），与当前完整本地状态合并为 S。正常增量同步仍可使用 seen；整理阶段不能把“在 seen 里”误当成当前内存持有该文件内容。最易审查的实现是整理时读取候选原文，直接计算覆盖关系，避免引入额外证明缓存。
2. 通过现有本地串行写队列保存合并结果与 seen，再发布 S。只有 MOVE 成功，且从最终 URL GET 回读校验哈希和完整状态成功，S 才成为远端删除依据。已有相同文件也必须先确认其远端内容有效，不能依赖上次枚举和旧的本地记忆。
3. 定义语义覆盖：S 对每个旧实体的每个 revision 都有时钟支配它的 revision；相同时钟还必须有规范化后完全相同的 value。未解决并发候选必须全部保留或被合法后继覆盖。应复用同一规范化/覆盖实现，不能用正文进度、修改时间、文件名时间或文件大小判断。
4. 删除仅限 C 中被已发布 S 覆盖的具体旧快照。严格支配时可删旧文件；状态语义相等时，以所有客户端一致的文件名字典序规则保留同一个最小者。整理者自己的新文件也不能凭“自己发布”抢占这一规则：若已有更小等价文件，保留已验证的更小文件作为依据。这样不会出现两个设备各删对方最后一份等价状态。不同 JSON 键序造成的不同哈希不代表严格支配，必须比较语义。
5. 绝不删除 C 之外的新文件，逐个 DELETE，不删除小说目录。新文件若与 S 并发，留待下一次合并；若远端另一个整理者将依据文件替换为更强状态，同一严格覆盖/等价固定次序规则保证证明链不会形成互删环。
6. 并发整理可使 LIST 后的 GET 返回 404。这属于明确的“目录已被并发整理”状态：重新枚举并重建整个整理计划，使用有界次数；持续变化或其他 HTTP 错误显式报告整理未完成。不得 catch 全部异常继续删除，也不得将权限失败当作已删除。DELETE 已不存在可按明确幂等语义处理，但不能忽略其他失败。
7. 用小批量阈值触发整理，或仅在有新发布且快照数量超过阈值时执行。阈值只决定何时整理，不决定删哪一份；不能用“只保留最近 N 份”替代覆盖证明。首次对现有积累文件整理可能读取全部，之后稳定期远端只留下因果上不能互相覆盖的少量末端状态。并发持续写入时不承诺固定一份。
8. seen 在一次成功重枚举后收敛为该 scope 当前仍存在、且已原子落盘合并的文件名；新发布的文件加入同一 scope。清理失败可以保留多余 seen 等待后续收敛，但绝不能把未读/未持久化的文件标已见。换服务器/账号/目录必须使用独立 scope。

**不可安全删除的内容：** 未解决冲突的候选、实体的删除墓碑、时钟中的离线设备维度、未知格式文件、无法验证的快照、未被 S 覆盖的并发状态、只在本地而未成功发布的唯一记录、其他客户端可能正在上传的 `.cache`。当前协议没有所有设备已退休/已确认删除的证明，不能按时间清墓碑或旧设备时钟；否则长期离线设备上线会复活已删书签。`.cache` 清理另需上传所有权/租约协议，不能仅凭“很旧”猜它没有活跃上传者。本轮先解决正常已完成快照积累，不把临时上传文件回收混入不安全捷径。

### 2. 冲突按记录与操作隔离

保留 `state.value` 遇冲突明确抛错及普通 edit 不可解决冲突的契约。服务层新增按操作列出依赖 key 的接口，UI 先展示相关状态，再执行依赖读取；不得全局 catch 冲突并返回任意第一候选。

| 冲突实体 | 限制的最小范围 | 其他操作必须继续 |
| --- | --- | --- |
| `position/<edition>` | 该书的继续位置选择、该进度写入；取消不改候选 | 其他书、书签独立记录、规则/外观/同步设置 |
| `bookmark/<id>` | 该书签的跳转/编辑/删除，需要显式选择或取消 | 同书正文继续读、其他书签、新建书签、其他书 |
| `selected/<edition>`、`source/<edition>/<source>` | 依赖该源选择/绑定的动作；明确传入另一正常源的动作按真实依赖判断 | 其他书与无关源、规则管理 |
| `edition/<id>`、`work/<id>`、`shelf/<edition>` | 对应书条目的信息/归属/上架修改；该行显示明确冲突入口 | 正常书架条目仍完整展示，不让整书架消失；不自动决定是否删除 |
| `chapterMap/<edition>/…` | 只有当前恢复动作实际使用到的这一条映射 | 其他章节和其他书；不得把映射冲突静默当“无映射”后猜章 |
| `anime/<animeId>` | 依赖该动画绑定的入口/修改 | 独立小说搜索与其他动画入口 |

冲突条目应展示书名、记录类型、章节/位置/书签说明和“保留删除”的明确选项；技术 ID 可作详情，不作为主要决策文案。书架的冲突概要入口可以保留，但不再强迫先清空全局列表。涉及同一书多个依赖时逐项处理，仅处理当前动作必需的集合。

选择安全契约：打开弹窗时捕获 **完整候选集合的规范化指纹** 和所选候选指纹；点击后在 `_writes` 队列内部重新读取当前集合，必须完全一致才 resolve。仅候选列表次序变化不应误报；新增、消失、内容或时钟变化均应明确提示“冲突已变化，请重新选择”，保留全部新状态。resolve 合并时钟并产生用户此次明确决定的新 revision。取消/系统返回/父路由已退出均不写任何状态、不继续依赖导航；异步结果须验证所属路由仍 active。不能只验证 `mounted`。

Reader 内收到该书进度冲突时暂停该 key 的自动写入并显示选择，不得把当前视口自动覆盖为赢家。取消选择不能修改冲突；若用户要退出且当前视口有尚未写入的新修改，必须明确说明未保存部分并由用户决定是否放弃退出，不能静默丢弃或擅自增添第三个云端候选。只读/无新改动的退出不应迫使用户先解决全局数据。设置本来是设备本地，不应增加与云端冲突的耦合。

### 3. `/novels/v1` → `/novels` 显式幂等迁移

目录去掉 v1，不等于删除 JSON 中的 schema version。新版唯一正常读写位置为 `/kazumiSync/novels`；原番剧收藏、历史、屏蔽词路径完全不变。迁移过程是可见状态，不是“新目录失败就悄悄读旧目录”的兜底。

1. 切换新 scope（服务器原始 URL、账号、新目录），不直接沿用旧路径 seen。若无旧目录正常初始化新目录；若存在旧目录，明确显示正在迁移旧小说数据，列举并验证旧/新两边参与的快照，合并全部因果状态和冲突。401/403/网络错误不能判为目录不存在。
2. 在新目录以不可变快照发布完整合并状态，GET 回读验证，原子保存本地 state 与新 scope seen，记录迁移阶段。任一失败都保留旧文件和本地数据；迁移未完成要显示错误及重试。重启重复执行相同合并/内容地址发布不会产生新的业务修订，不会靠 wall-clock 覆盖。
3. 只有新目录已存在可验证覆盖依据，才逐个删除本轮明确枚举且被覆盖的旧快照。并发新到旧文件不在删除集合内，后续重新发现并迁移。未知文件/活跃 `.cache` 不递归删除，不宣称旧目录已经清空。
4. **无法同时保证“旧版持续使用 v1”与“彻底删除 v1 并透明双向同步”。** 旧版不会读新目录，也不会遵守新迁移标记。需明确要求其他设备升级或停止旧版小说同步；保留本地离线数据后升级的新客户端可以直接与新目录合并，因果/墓碑不能因迁移删掉。
5. WebDAV 删除 collection 通常是递归 DELETE。先 readDir 为空再 `client.remove('/v1')` 仍有竞态：旧设备能在两请求间写入。没有已验证服务器强条件机制/写入静止条件时，不能自动删除 collection。应在所有旧写入者停止且不存在在途上传的维护窗口确认旧目录只剩已迁移文件，逐项清理后再删除目录；未满足条件则明确“数据已迁移，旧目录清理待完成”，不得伪报去目录成功。
6. 已完成迁移后若再次发现旧版写入 v1，应明确报告旧客户端仍在写旧目录并进入同一可见迁移流程；正常同步不得静默双写或回退旧目录。根目录的其他文件及官方所有路径均在删除白名单之外。
